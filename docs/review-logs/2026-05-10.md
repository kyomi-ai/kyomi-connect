| # | Severity | Anti-Pattern Category | File:Line | Description |
|---|----------|----------------------|-----------|-------------|
| 1 | 🟡 | State Management | `executor.rs:468-471, 535-550` | `discover_tables` and `discover_columns` call `extract_string_col_from_batch` independently on columns 0, 1, and 2, then zip/index-align the resulting vectors. `extract_string_col_from_batch` filters out null values (compacting the vector). If any non-primary column has a null in row N, that null is dropped and every subsequent value shifts left — the zip/index then pairs the wrong name with the wrong type or description. The original `rows`-based code was per-row (positionally correct). The fix must iterate batch rows directly rather than making independent per-column extractions. |

**Anti-pattern tally**: State Management ×1 (misaligned null-compacted vectors treated as positionally aligned)

**Notes**: The null-compaction misalignment will not manifest for standard SQL catalog queries because `table_type`, `data_type`, and `engine` are effectively non-null in all supported databases. However, the pattern is structurally incorrect and dangerous — it would silently produce wrong catalog data if any metadata column ever returns a null (e.g. ClickHouse `comment` column, which is frequently empty-string but sometimes null). The correct fix is a helper that iterates batch rows, or a row-zip helper in `provider.rs` that returns `Vec<Vec<Option<String>>>` indexed by row then column.
